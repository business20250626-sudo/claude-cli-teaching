Chapter 9 權限模式 — 「問你」與「放手」之間的旋鈕

⏱ 預估 9 分鐘讀完,加上小練習共 20 分鐘

💡 一句話講完

Claude 每次想改檔、跑指令、發網路請求都會停下來問你。權限模式就是控制「這個停頓多常發生」的旋鈕 — 從「每件事都問我」到「放手讓它做」,你按 Shift+Tab 切換。敏感工作用緊一點的、信任方向時用鬆一點的。

為什麼需要它:在「煩」和「險」之間取捨

兩種極端都不好用:每個動作都要你批准 → 煩,做一個小功能按二十次 Enter;什麼都不問直接做 → 險,它改錯方向或被 prompt injection 帶壞你也來不及攔。

權限模式讓你依當下的工作性質調這個旋鈕:在不熟的正式環境調緊、自己掌控每一步;在你會事後 review 的迭代階段調鬆、讓它連續做久一點再回報。一共六種模式,但它們分成兩群 —— 日常四種(按 Shift+Tab 切)和特殊兩種(要用旗標才叫得出來)。

日常四模式:Shift+Tab 循環切換

這四種是你天天在用的。在 session 裡按 Shift+Tab 就會循環切,目前模式顯示在狀態列。由緊到鬆:

模式不用問就能做的事什麼時候用
default
(預設)		 只有讀取 起步、碰敏感東西 — 每個改動都要你點頭
plan
(計畫模式)		 只有讀取,而且連改都不准 動手前先探索、提計畫對齊方向(見下方)
acceptEdits
(自動接受編輯)		 讀 + 改檔 + 常見檔案指令(mkdir / touch / mv / cp 等) 你會事後用 git diff 一次看完,不想逐個批准
auto
(自動模式)		 幾乎全部,但有分類器在背景把關 長任務、減少打斷,但你信任大方向
📐 plan mode 的重點不是「省去問你」,是「動手前先對齊」

plan mode 跟 default 一樣只能讀,但它連改都禁止 — 只能研究你的 codebase、然後產出一份計畫給你看。等你核准計畫,它會切到你選的模式(auto / acceptEdits / 逐個確認)才開始改。這是非平凡改動的核心習慣:先看它打算怎麼做、確認方向對了,再放它動手,避免「悶頭改一堆、改錯難收拾」。隨手用:任一句話前面加 /plan,或按 Shift+Tab 切進去。

⚠️ auto 模式:減少 prompt ≠ 保證安全

auto 模式幾乎什麼都不問你,但背後有個獨立的分類器模型逐個動作把關:偵測到「超出你要求的事」「碰到不認識的基礎設施」「像被惡意內容帶風向」就擋下(預設擋 curl|bash、正式環境部署、force push、推 main 等)。但官方明講它是研究預覽,「減少 prompt 不代表保證安全」,而且有方案 / 模型 / 版本門檻 —— 帳號不達標時 Shift+Tab 根本不會出現它。

特殊兩模式:要用旗標才叫得出來

這兩種故意不放進 Shift+Tab 循環,因為它們不是「隨手切換」的東西 — 一個給無人環境、一個有風險,都得在啟動時明確指定:

模式行為怎麼啟用用在哪
dontAsk 凡是會跳出來問的一律自動拒絕,只跑你預先 allow 的工具 claude --permission-mode dontAsk
(永遠不在循環裡)		 要 LLM 的幫助,又要固定它的工具
bypassPermissions 所有檢查全關,工具直接執行 claude --dangerously-skip-permissions
(要重啟才出現在循環)		 只能用在隔離的容器 / VM
🤔 兩個特殊模式,被踢出循環的理由剛好相反

bypassPermissions 是太危險(怕你手滑切到零檢查);dontAsk 是太死板、非互動 —— 切過去後,沒預先 allow 的動作它默默拒絕、不問你,你會一臉問號「怎麼叫它幹嘛都不動」。它是為「無人值守」設計的,放進日常隨手切的循環只會害人誤觸。所以兩個都要明確下旗標,不放進 Shift+Tab。

🚨 bypassPermissions:對 prompt injection 毫無防護

官方原話:這個模式「對 prompt injection 和意外操作毫無防護」。一般 session 切不進去,必須用危險旗標重啟;在 root / sudo 下還會直接拒絕啟動。除非你在「就算它搞砸也傷不到主機」的隔離容器裡,否則別用 —— 想要「少問又安全」,用 auto 模式,不是這個。

怎麼切換

# session 中:循環切日常模式
Shift+Tab          # default → acceptEdits → plan(達標的話再加 auto)

# 啟動時指定
claude --permission-mode plan

# 設成專案 / 個人預設(settings.json)
{
  "permissions": { "defaultMode": "acceptEdits" }
}

模式、規則、hook:三層怎麼疊起來

這章的權限模式,跟你前面學過的 /permissions和 hook不是三選一,而是三個層次疊在一起:

層次管什麼本質
權限模式(本章) 整體底線 — 這個 session 大致上多常問你 一個旋鈕,Shift+Tab 切
/permissions 規則 個別工具放行 / 問 / 擋,疊在模式之上 內建的 allow / ask / deny 規則
hook 用程式邏輯做「符合某條件才攔」的客製判斷 你寫的程式,綁在事件點

官方原話:模式設底線(set the baseline),規則疊在上面。而且 deny 規則和明確的 ask 規則在每個模式都生效 —— 連 bypassPermissions 也擋得住。所以即使開了很鬆的模式,你仍能用一條 deny 規則保住絕對不能碰的東西。

怎麼分辨「這件事該用哪一層」

三層最容易混。用這三個問題對號入座:

你的需求長這樣用哪一層為什麼
「這一整段工作我想少被打斷 / 想先看計畫」
例:這次重構讓它連續做、做完我再看		 權限模式 模式是整個 session 的氛圍,隨手 Shift+Tab 調,不針對特定工具
「某類動作固定要放行 / 固定要問 / 絕對禁止」
例:npm test 別再問了、git push 一定要問、永遠不准碰 .env		 /permissions 規則 規則是常駐的、針對工具+參數的白/灰/黑名單,設一次長期有效
「要看情況、帶條件判斷才能決定擋不擋」
例:只有 push 到 main 才擋、改到某些檔要先跑檢查		 hook 規則只會比對字串,表達不出條件邏輯;hook 是你寫的程式,想多聰明都行

一句話:調整體氛圍 → 模式;某類動作一律怎樣 → 規則;要看情況判斷 → hook。

細看中間這層:/permissions 規則

前面幾章一直提到它,這裡正式講清楚。打 /permissions 開互動介面,或直接寫進 settings.json。規則分三種:

  • allow:符合的工具呼叫直接放行,不問你
  • ask:符合的每次都跳出來問你
  • deny:符合的直接擋掉,Claude 連試都不能試

評估順序:deny → ask → allow(先中先贏)

官方原話:"Rules are evaluated in order: deny, then ask, then allow." 三種規則同時存在時,deny 最優先,其次 ask,最後 allow,而且規則細不細不影響順序 —— 就算有一條更精確的 allow,只要也中了一條 ask,還是會問你。這個設計讓「擋」和「問」永遠蓋得過「放行」,安全性才守得住。

語法:工具名 或 工具名(條件)

{
  "permissions": {
    "allow": [
      "Bash(npm run *)",      // npm run 開頭的指令都放行
      "Bash(git commit *)"
    ],
    "ask": [
      "Bash(git push *)"      // push 一律先問我
    ],
    "deny": [
      "Read(./.env)",         // 永遠不准讀 .env
      "Bash(rm -rf *)"
    ]
  }
}
  • 不帶括號 = 整個工具:Bash 比對所有 Bash 指令、Read 比對所有讀檔。
  • 括號裡是條件,Bash 支援 * 萬用字元:Bash(npm run *) 比對 npm run 開頭的指令。注意空格很重要 —— Bash(ls *) 配得到 ls -la 但配不到 lsof;Bash(ls*)(沒空格)兩個都配。
  • 檔案規則用 gitignore 風格路徑:Read(./.env) 當前目錄的 .env、Edit(/src/**/*.ts) 專案根的 src 底下、Read(~/.zshrc) 家目錄、Read(//tmp/x) 才是絕對路徑(兩條斜線)。
  • 網路 / MCP:WebFetch(domain:example.com)、mcp__notion__*(某 server 的全部工具,接 Ch7)。
⚠️ 別用 Bash 規則「限制參數」來做安全控制

官方明確警告:想用 Bash(curl http://github.com/ *) 把 curl 限制在某網域很脆弱 —— 換個寫法(https、選項放前面、用變數、多個空格、短網址轉址)就繞過去了。要擋網路請改用 deny 掉 curl/wget + 用 WebFetch(domain:...) 開白名單,或用 hook 驗證。規則適合「這個指令前綴放不放行」,不適合「這個指令的參數安不安全」。

存哪、誰蓋過誰

規則寫在 settings.json,跟前幾章一樣分層,而且deny 不分層級一律最大:

  • .claude/settings.json(專案共用,commit 進版控)、.claude/settings.local.json(個人、不進版控)、~/.claude/settings.json(你所有專案)
  • 官方原話:"If a tool is denied at any level, no other level can allow it." —— 任何一層 deny 掉,其他層都救不回來。所以團隊可以在專案 settings 放一條 deny 守住絕對紅線,個人設定鬆歸鬆都蓋不掉。
🛠 小練習:用同一個任務,感受三種模式的差別

步驟

  1. 找個小改動需求(例如「幫遊戲頁面的某個文字改個顏色」)。先在 default 模式下叫 Claude 做,觀察:它每要改一個檔就停下來問你。
  2. 按 Shift+Tab 看狀態列循環變化,切到 plan 模式,下同一個需求:它不會動手,只給你一份「我打算怎麼改」的計畫。看過、確認方向對了再核准 — 體會「先對齊再動手」。
  3. 再 Shift+Tab 切到 acceptEdits 模式(狀態列顯示 ⏵⏵ accept edits on),下需求:它直接改、不問你,你事後用 /diff 或 git diff 一次檢視。
  4. (加一條規則)打 /permissions,加一條 ask 規則 Bash(git push *)。然後不管你切到多鬆的模式(連 acceptEdits),叫它 push,它都會先問你 —— 體會「規則疊在模式之上、ask 蓋過放行」。想更硬就改成 deny,它連試都不會試。

練習目的

  • 親手用 Shift+Tab 切換,看狀態列怎麼變
  • 感受三種模式的「問你頻率」差異:default 逐個問、plan 先給計畫、acceptEdits 直接做
  • 用一條 /permissions 規則,看到「規則疊在模式上、deny/ask 蓋過放行」
