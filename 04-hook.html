Chapter 4 Hook — 在固定事件點「一定會跑」的程式

⏱ 預估 8 分鐘讀完,加上小練習共 20 分鐘

💡 一句話講完

Hook 是綁在 Claude Code 生命週期特定事件點上的觸發機制:到點就觸發,(部分事件)再由 matcher 篩、由 handler 決定動作。跟 CLAUDE.md 最大的差別 —— CLAUDE.md 是軟性建議(不保證遵守),Hook一定會執行的程式,不管 Claude 想不想。

為什麼需要它:接續 Chapter 3 的伏筆

Chapter 3 講過,CLAUDE.md 是 context、不保證被遵守。所以如果某件事「一定要在某個時間點發生」——例如每次 commit 前一定要 lint、每次改完檔一定要格式化——寫在 CLAUDE.md 不夠保險。

Hook 就是硬性版的解法:它在固定事件點執行,是真正會跑的 shell / 動作,不靠 Claude「願不願意」。

運作:三段式

  1. 事件點(event):生命週期跑到某個點(例如「工具呼叫前」)
  2. matcher(篩選,部分事件才有):符合條件才往下(例如只在用 Bash 工具時)
  3. handler(動作):真正要跑的東西(跑 shell、丟給 LLM、POST 到端點…)

常見的事件點

事件其實很多,這裡列幾個最常用的(完整清單見官方 hooks 文件):

事件什麼時候觸發
SessionStartsession 開始或恢復時
UserPromptSubmit你送出 prompt、Claude 處理前
PreToolUse工具呼叫執行前(可以攔下來)
PostToolUse工具呼叫成功後
StopClaude 回完一輪時
SessionEndsession 結束時

matcher:篩「哪些情況才觸發」

matcher 主要用在 tool 相關事件,用工具名來篩:Bash、Edit|Write(兩者皆可)、mcp__.*(正則)。

⚠️ 不是每個事件都有 matcher

像 UserPromptSubmit、Stop 沒有 matcher,到點一定觸發。對這些事件寫 matcher 會被無視。matcher 主要是給 PreToolUse / PostToolUse 這類「想針對特定工具」的場景用的。

handler:觸發後跑什麼(5 種,三個類別)

類別type做什麼
規則 command 跑一段 shell 腳本;事件的 JSON 從 stdin 進去,用 exit code / stdout 回報結果
委派判斷 prompt 把 prompt 丟給 Claude 模型做單次 yes/no 判斷,回傳 JSON 決定
agent ⚠️ 實驗性 生一個 subagent,可用 Read / Grep / Glob 等工具查證後再回判斷(官方標 experimental,可能會變)
外送 / 接外部 http 把事件 JSON 以 HTTP POST 丟到一個 URL,用回應(同樣的 JSON 格式)決定
mcp_tool 呼叫一個已連線的 MCP server 上的工具,工具的文字輸出當成 command 的 stdout 處理

可能的使用情境

用「你最希望它每次都做的事」來想最有共鳴。這些寫在 CLAUDE.md 可能被忘記,寫成 hook 就是每次必跑:

你的擔憂 / 期望hook 怎麼幫你事件 + matcher → handler
「怕它說『好了』其實根本沒驗證」 改完檔自動跑測試 / type check,壞了把錯誤回報給它當場修 PostToolUse + Edit|Write → command
「跑很久,我跑去做別的事會錯過」 完成一輪就叮一聲 / 發通知到 Slack,不用一直盯著 Stop → command 或 http
「想知道它到底對我專案做了什麼」 把每個執行過的指令記進一份 audit log,事後可追 PostToolUse + Bash → command
「希望一開工就有完整背景」 session 開場自動報告專案當前進度、今天待辦事項等等 SessionStart → command
「怕它手滑跑出毀滅性指令的各種變形」 執行前可靠擋下 git push -f / --force-with-lease / +main 等所有寫法(本章小練習) PreToolUse + Bash → command
⚠️ 等等,擋危險指令不是 /permissions 的事嗎?

對,擋固定指令、擋讀某個檔(.env)這種,用 /permissions 的 deny 規則就好(Chapter 9),不必動用 hook。那為什麼最後一列還用 hook 擋 force push?

因為 permission 規則是字串比對,防不了變形規避 —— 官方自己警告 Bash 參數規則「很脆弱」。你寫 deny: Bash(git push --force *),擋得住這個拼法,卻擋不住 git push -f、--force-with-lease、git push origin +main、用變數繞過⋯ hook 是程式,能解析、正規化指令,把所有變形都收斂成「這在 force push」一律擋。高風險、又有多種寫法的東西,才值得從規則升級成 hook。

看出規律了嗎:hook 的獨特價值在兩種情況 —— (1) 根本不是「擋/放」,而是反應(跑測試、通知、記錄、注入 context);(2) 要可靠擋掉某「類」東西、防變形規避,規則的字串比對不夠力。只是「擋固定 pattern」用 /permissions 規則更省事。
