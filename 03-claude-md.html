Chapter 3 CLAUDE.md — 每次自動載入的專案常駐指示

⏱ 預估 8 分鐘讀完,加上小練習共 20 分鐘

💡 一句話講完

CLAUDE.md 是一份由你掌控的純文字檔(內容你說了算——自己打,或用 /init、叫 Claude 幫你產都行),每次 session 開頭完整載入,放你的持久指示 —— build 指令、程式慣例、架構規則,分組織 / 使用者 / 專案 / 本機四層。

為什麼需要它:每次對話都是新的

Claude Code 每次啟動都是全新的上下文視窗。它在同一次對話裡記得脈絡,但你關掉再開,先前講過的事就忘了。於是你會一直重複:

  • 「這個專案用 pnpm test 跑測試,不是 npm」
  • 「API handler 放在 src/api/handlers/」
  • 「commit 用 Conventional Commits,先 add 再 commit」
  • 「動 infra/ 之前一定要先問我」

CLAUDE.md 就是解法:寫一次,之後每次對話 Claude 都已經知道。

放哪裡:四個層級,由廣到窄

Claude Code 會從你啟動的目錄一路往上找 CLAUDE.md,把找到的全部疊在一起送進 context。順序是從最外層往你的工作目錄,所以越貼近專案的排在越後面。

層級 位置 適合放什麼
企業政策
(IT 部署)		 macOS: /Library/Application Support/ClaudeCode/CLAUDE.md 全公司的安全 / 合規守則,個人無法覆寫
個人全域 ~/.claude/CLAUDE.md 跨所有專案的個人偏好:語言、commit 風格、慣用工具
專案
(隨 git 共享)		 ./CLAUDE.md 或 ./.claude/CLAUDE.md 團隊共用:build/test 指令、架構、命名慣例、工作流程
本機私人 ./CLAUDE.local.md(記得加進 .gitignore) 只屬於你的:本機 sandbox URL、偏好的測試資料

多個層級可以同時存在,Claude 會全部讀進去。但要注意:排在後面不代表一定優先 —— 它們都只是 context,萬一兩層互相矛盾,Claude 可能隨便挑一條。所以重點不是排序,而是別讓它們打架,定期回去清掉衝突或過時的條目。

怎麼寫才有效

CLAUDE.md 每次都會佔上下文額度,而且它是「參考」而非強制規則。寫法直接影響 Claude 遵守的程度。三個原則:

  • 夠具體、可驗證:「用 2 格縮排」勝過「程式碼要排版整齊」;「commit 前跑 pnpm test」勝過「記得測試」
  • 有結構:用 Markdown 標題和條列分組,Claude 跟人一樣比較好掃
  • 不要太肥:目標 200 行以內。越長越難遵守。一次性的別寫,只寫每次都受用的

一份適合專案根目錄的 CLAUDE.md 起手式:

# 專案概述
## 1. 動手前先想
- 講出你的假設;不確定就問。
- 有多種解讀就攤開來,別默默選一個。
- 有更簡單的做法就說,該擋就擋。

## 2. 簡單優先
- 只做被要求的,不要多做、不要臆測需求。
- 單次使用的程式碼別硬加抽象層或「可設定性」。
- 50 行能寫完就別寫 200 行。

## 3. 精準修改
- 只動非改不可的;不要順手美化隔壁的程式、註解、排版。
- 沒壞的不要重構;配合既有風格,即使你會用別的寫法。
- 清掉「你的改動」造成的孤兒(沒用到的 import / 變數);既有死碼除非被要求別刪。

## 4. 目標導向
- 把任務變成可驗證的目標:
  - 「加驗證」→ 先寫不合法輸入的測試,再讓它通過
  - 「修 bug」→ 先寫能重現的測試,再讓它過
- 多步驟任務先講一個簡短計畫,每步附上「怎麼驗證」。

## 5. 溝通偏好
- 用台灣繁體中文回我,技術名詞保留原文;回答簡潔
- 不確定就說不確定,不要編造
- 重大或不可逆的動作(刪檔、force push、改 CI)先列計畫,等我點頭再做

## 6. 安全
- 不要把密鑰 / token 寫進程式碼、commit message 或 log
- 不確定能不能對外送的資料,先問我

## 7. Git / 專案管理規範
- 在適當情況下使用清楚的 commit 訊息
- 避免在同一次修改中混合不相關的變更
- 未經明確要求，不要自動對整個專案進行格式化
⚠️ CLAUDE.md 是「軟性」指引,不是防護欄

CLAUDE.md 的內容是當作上下文餵給 Claude,不保證 100% 遵守,尤其指令模糊或互相矛盾時。如果某件事「一定要在某個時間點執行」(例如每次 commit 前),用 Hook 來強制,而不是寫在 CLAUDE.md。

三個一定要會的工具

指令 / 語法 做什麼
/init 讓 Claude 掃過你的 codebase,自動生成一份起手 CLAUDE.md(build 指令、測試方式、慣例)。已有檔案時會建議改進而非覆蓋。
/memory 列出目前這次對話載入了哪些 CLAUDE.md / rules 檔,點開就能編輯。Debug「Claude 怎麼沒照做」時第一步。
@path/to/file 在 CLAUDE.md 裡 import 別的檔,例如 git 規範 @docs/git.md。被引入的檔一樣會在啟動時載入。
💡 別跟 auto memory(自動記憶)搞混

CLAUDE.md 由你決定內容(就算請 Claude 用 /init 幫你產,也是你審、你 commit、放進你的 repo);auto memory 是 Claude 自己判斷該記什麼、不用你開口 —— 它從你的修正裡發現並記下你的習慣(build 指令、debug 心得)。差別在誰主導。

還有一個差異:auto memory 只載入 MEMORY.md 的前 200 行 / 25KB;CLAUDE.md 則是完整載入。

🛠 小練習:幫一個真實 repo 建 CLAUDE.md

感受「Claude 永遠記得這個專案怎麼跑」的差別。

步驟

  1. 在你某個專案資料夾開 Claude Code,輸入:

/init

Claude 會掃描專案、生成一份 CLAUDE.md 草稿。

  1. 打開生成的 CLAUDE.md,補一條 它不可能自己猜到的規則,例如:

每個回覆一開始都跟我說一聲尊貴的主人您回來啦～

  1. 關掉對話、開新對話,隨便問個問題看看claude是否有主動引用你寫的指令。
  1. 輸入:

/memory

可以查看當前載入了哪些 CLAUDE.md

練習目的

  • 體驗 /init 怎麼自動產生起手式
  • 看出 CLAUDE.md 怎麼影響「下一次」對話的行為
  • 明白以後不用每次重新交代專案怎麼跑
✅ 走完 Chapter 3 你要能...
  • 說出 CLAUDE.md 是什麼(每次自動載入的常駐指示,不是模型在「記憶」)
  • 知道四個放置層級,以及專案級 vs 個人全域的差別
  • 寫出具體、可驗證、不臃腫的指令
  • 會用 /init 生成、用 /memory 檢查載入狀況
  • 知道 CLAUDE.md 是軟性指引,強制行為要用 Hook
