Chapter 8 Subagent — 委派出去的專門角色

⏱ 預估 9 分鐘讀完,加上小練習共 20 分鐘

💡 一句話講完

Subagent 是把一個專門角色(含它的工具權限與行為設定)封裝起來,主任務在合適時(通常自動)委派給它,讓它在獨立的上下文裡完成工作後只回報結果。好處是脈絡隔離、可平行、配置專門化。

為什麼需要它:主對話會被「過程」塞爆

想像你叫 Claude「找出這個 codebase 哪裡處理付款」。它會讀一堆檔、grep 一堆關鍵字、印出大量結果 — 這些過程全部堆進你的主對話 context。等它找到答案,你其實只想要那一句結論,但前面那堆搜尋雜訊已經佔滿了視窗,還會稀釋後面的對話。

Subagent 就是解法:把這種「會產生一堆你之後不會再看的輸出」的工作,丟給一個有自己獨立 context 視窗的子代理去做。它在自己的視窗裡讀檔、搜尋、翻找,做完只把結論回報給主線 — 過程的雜訊留在它那邊,不污染你的主對話。

兩個核心優勢

1. 固定了「角色、行為與工具權限」

一個 subagent 不只是「另一個 Claude」,而是一個被你定義好的角色:你給它專屬的 system prompt(它是誰、該怎麼做事)、指定它只能用哪些工具、用哪個模型。

工具權限這點特別有用 — 例如一個「code reviewer」只該讀不該改,你就只給它 Read / Grep,不給 Edit。這樣就算它判斷錯誤想動手,也動不了,因為它手上根本沒有那個工具。這是比「拜託它別改」更硬的保證。

2. 節省上下文(但有代價)

subagent 只回傳結果,中間過程不會回流到主 session 干擾你。這就是省 context 的關鍵。

⚠️ 代價:彼此看不到脈絡

隔離是雙面刃。子代理跟主線之間、子代理彼此之間,都看不到對方的脈絡 — 子代理開工時是一張白紙,只拿到主線交付的那段任務描述,完成後也只吐回一段結論。

所以:任何需要子任務互相參照、傳遞中間結果、來回討論的工作,用 subagent 就不太適合。那種工作留在主對話做,或改用 skill(在主線 context 裡跑)。

怎麼建自訂 subagent

跟 skill 一樣是「資料夾 + Markdown 檔」的概念,但 subagent 放在 .claude/agents/,一個 agent 就是一個 .md 檔:frontmatter 設定 + 內文(就是它的 system prompt)。官方範例:

---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.
frontmatter作用
name(必填)agent 識別名,小寫加連字號
description(必填)講「這在幹嘛、何時該派它」— Claude 靠它判斷要不要委派,寫得好才會在對的時機被叫
tools(選填)限定它只能用哪些工具;不寫就繼承主對話的全部
model(選填)指定模型 — 簡單任務可以派便宜的 Haiku 省錢

不用手寫也行:打 /agents 開互動介面建立(而且立刻生效;手動改檔案則要重開 session)。

🔗 跟 Skill 怎麼選?

兩個都能封裝「可重複使用的角色 / 流程」,差別在跑在哪個 context:skill 在主對話裡跑(看得到你的完整脈絡,適合要來回討論的工作);subagent 在隔離的 context 裡跑(看不到主線脈絡,適合會產生一堆雜訊、只要結論的自包含任務)。需要頻繁來回、共享脈絡 → 主對話或 skill;會洗版、只要結果 → subagent。

🛠 小練習:建一個唯讀的 code-reviewer,看「工具權限」真的把它鎖住

步驟

  1. 打 /agents,建一個新的專案 subagent(或直接手寫 .claude/agents/code-reviewer.md):
    2. ---
name: code-reviewer
description: 審查程式碼品質與最佳實踐,只讀不改
tools: Read, Glob, Grep
model: sonnet
---

你是程式碼審查者。被叫用時,分析程式碼,針對品質、
安全性、最佳實踐給出具體、可執行的建議。不要修改任何檔案。
  2. 將cmd/slot-verify/main.go的第16行func故意刪掉c,然後點名它來看:
    3. 用 code-reviewer subagent 看一下main.go
  3. 觀察:它會在自己的 context 裡讀檔、分析,回報一段審查意見 — 注意主對話沒有被一堆讀檔過程洗版,只多了那段結論。
  4. (權限驗證)接著叫它動手改:「順便幫我把那個問題修掉」。因為它的 tools 只有 Read, Glob, Grep、沒有 Edit,它改不了 — 你會看到它要嘛說自己沒有修改工具、要嘛把修改建議丟回給主線由主 Claude 處理。這就是「工具權限」比口頭約束更硬的地方。
    5.  用 code-reviewer subagent 幫我修復main.go的bug

練習目的

  • 走一次完整流程:建 agent → 點名委派 → 拿回結論
  • 親眼看到脈絡隔離:審查的讀檔過程沒進主對話
  • 驗證工具權限:不給 Edit,它就真的改不了,而不是「拜託它別改」
