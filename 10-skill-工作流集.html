Chapter 10 兩套工作流 skill 集 — superpowers vs mattpocock/skills

⏱ 預估 13 分鐘讀完,加上小練習共 30 分鐘

💡 一句話講完

不必從零寫 — 社群已經把成套的工作流打包好。這章挑兩套最具代表性、理念又剛好相反的:obra/superpowers 是一條強制的端到端開發流水線(管你「怎麼做事」);mattpocock/skills 是一組分類好、挑著用的工作流工具箱(給你「某個時刻該出的招」)。

為什麼要看這個:從「自己寫 skill」到「用工作流 skill 集」

成熟的工作流(完整的 TDD 循環、code review 流程、把對話變成 issue…)往往要寫好幾個互相搭配的 skill、還要反覆打磨。與其從零開始,直接裝一套別人調校好的 skill 集通常更划算。

市面上的 skill 集很多,這章挑這兩套,是因為它們的設計哲學剛好站在對立面 —— 看懂它們的差異,你就抓得到「工作流 skill 集」這一整類東西的兩條典型路線,也知道自己的情境該裝哪個。

兩種思考哲學:它們在「防」的東西剛好相反

這兩套其實在回應同一個 AI 時代的問題:AI 讓你產出 code 的速度,遠超過你能驗證它對不對、或維持它協調的速度。但它們選擇防的失敗模式剛好相反 —— 一個防「執行不可靠」,一個防「方向錯、設計爛掉」。先抓住這層世界觀,再看各自的 skill 設計就會覺得「合理、各有取捨」。

📋 抓重心:完整照走 vs 前重後輕

superpowers 把流程寫得很完整,你照著走就好 —— 每一步都規定好(brainstorm → plan → TDD → review → verify),好處是不容易走歪、代價是儀式偏重。mattpocock 整體沒那麼「一條龍」,重心擺在前面:把定義與對齊做得很講究(grilling 逼問、PRD、垂直 issue、ADR),但後面怎麼執行就放手讓你自由發揮 —— 挑哪個 skill、怎麼接,你決定。

superpowers 的世界觀:不信任 agent,所以上鐵軌

  • 想解決的問題:agent(和人)最危險的傾向是「猜」 —— 跳到一個聽起來很對、其實沒驗證過的答案,然後宣稱完成。
  • 解決方法:把紀律寫成繞不過去的鐵軌。using-superpowers 那句「1% 機率適用就絕對必須叫用」就是個 forcing function —— 不寄望 agent 自律,直接上鎖。它的口號也很直白(repo 原話):"Process over guessing"(別用猜的)、"Write tests first, always"(測試永遠先寫)、"Verify before declaring success"(有證據才算完成),並持續 "complexity reduction"(簡化)。
skill名稱實際會做的事
using-superpowers 入口 skill,開場 hook 自動載入,逼 Claude 每次任務前先找適用的 skill 再動作

subagent-driven-development 主agent會去讀剛剛的plan,使用不同的agent去做如下skill: using-git-worktrees -> test-driven-development -> requesting-code-review -> finishing-a-development-branch

writing-skills 寫 / 改你自己的 skill(含驗證 skill 好不好用)

mattpocock 的世界觀:信任人,給他的判斷裝槓桿

  • 想解決的問題:沒對齊("No-one knows exactly what they want")和設計腐敗。寫 code 不難,難在知道要做什麼、以及隨時間保持系統可理解。
  • 解決方法:不上鎖,而是給你在對的時刻主動叫的鋒利工具 —— 逼問(grilling)釘死需求、domain-modeling 建共用語彙、CONTEXT.md / ADR 記住決策。agent 是要「對齊」的協作者,不是要「上鎖」的對象。
skill名稱實際會做的事
ask-matt 路由器:不確定該用哪個時,問它「這情況適合哪個 skill / flow」
setup-matt-pocock-skills 專案當案基礎設定
grill-with-docs 確認專案脈絡 -> 專案內容詢問 ->生成CONTEXT.md及adr相關文件
domain-modeling 持續打磨領域模型:挑戰用詞、用情境壓力測試,就地更新 CONTEXT.md 與 ADR
prototype 決策上的疑問就可以先實際跑看看,可與grill-with-docs搭配使用
to-prd 生成PRD,內容包括標題、Problem Statement(问题陈述)、Solution(解决方案)、User Stories:需求清单(角色+想要+好处)」,——它穷举需求,供下游切片时逐条对应、Implementation Decisions(实作决策)、Testing Decisions(测试决策)、Out of Scope(范围之外) —— 记这次明确「不做」的东西。这栏看似不重要,其实很关键:它防止后面接手的 AFK agent gold-plating(自作主张多做)

tdd 紅綠重構迴圈,一次一個垂直切片(implement 會叫到)

流程列出來幾乎一樣 —— 那細節差在哪?

把兩套的階段攤開,你會發現它們幾乎一對一:都先對齊 → 規劃 → 切片 → TDD → review → 驗證 → 收尾。所以真正的差別不在「有哪些步驟」,而在每一步怎麼被執行、產出什麼、誰在驅動。歸成以下維度:

維度superpowersmattpocock/skills
誰驅動流程 流程驅動你:skill 自動觸發、強制(1% 原則 + 開場 hook);你核准設計後,大多在「看它跑」 你驅動流程:多是 / 指令,你在對的時刻主動叫;全程由你決定
記憶留多久 即拋:活在這次的 plan 檔,任務結束就散 累積:決策寫進 CONTEXT.md / ADR,跨天、跨任務疊加
品質從哪來 流程紀律 + 驗證證據(機械、可重複):TDD、verification-before-completion、不討好的 code review 對齊 + 設計 + 共用語彙(靠判斷、人在迴圈):grilling、domain-modeling、每天投資設計

所以「流程很像」是表象;真正的分水嶺是 ① —— 一套把紀律變成你逃不掉的軌道,一套把能力變成你隨手取用的工具。②③④ 其實都從 ① 長出來:被流程推著走,記憶就只需活到任務結束;自己開車,就得把決策留在 CONTEXT.md 裡、下次才接得上。下面兩節分別細看兩套的招式。

你的情況 → 選哪個(可以兩套並用)

你的情況 / 需求選為什麼(對應差異 / skill)
想強制「每個任務都先想、先測、先驗」的工程紀律 superpowers forcing function,紀律逃不掉(誰驅動)
要 AI 宣稱完成前先跑驗證、拿出證據 superpowers verification-before-completion(品質)
想在多個 AI 工具(Codex / Cursor / Gemini)用同一套方法 superpowers 明確跨平台
要把討論變成 issue / PRD、接上團隊 issue tracker mattpocock to-issues / to-prd / triage
想累積專案決策記憶(CONTEXT.md / ADR)、跨天接得上 mattpocock domain-modeling / handoff(記憶)
只想用「某一招」(如只把對話變 issue),不想被整套綁 mattpocock 自助餐、挑著用(誰驅動)
既要強制紀律,又要團隊產物與長期記憶 兩套並用 superpowers 當底層紀律 + mattpocock 的 /to-issues、/grill-with-docs

作家的小murmur

  • matt的grill-with-docs個人覺得非常好用,詢問較深,且會生成出專案共用詞彙及架構討論等等檔案,有利於未來專案的運作
  • matt的to-issue使用的是垂直切割,可以在每個issue內都能寫一條端到端的測試
  • 推薦的兩個都沒有做到整合測試的部分,可以使用claude內建的/verify來完成這部分
  • 兩個方法其實都不錯可以混著用,也可以透過改寫skill來做到對方沒有做的事情
